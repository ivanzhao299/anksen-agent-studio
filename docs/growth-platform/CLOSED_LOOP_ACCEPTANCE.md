# ANKSEN AI Growth Platform — Closed-loop Acceptance

## Product closure
A tenant must be able to execute: discovery → identity resolution → lead → explainable score → engagement → next-best-action → qualified opportunity → downstream handoff → revenue attribution → management report.

## Mandatory gates
1. Core contains no KingTurf-specific logic.
2. Every authoritative object/event is organization/workspace/tenant scoped.
3. Cross-tenant operations fail closed.
4. Channel adapters declare capability, risk and approval policy; official API/webhook is preferred.
5. External writes are idempotent/auditable; high-risk automation remains optional.
6. Score is explainable and versioned.
7. Identity resolution deduplicates repeated discovery.
8. Opportunity handoff uses an adapter boundary; CRM/ERP remains authoritative downstream.
9. Revenue attribution references opportunity and lead.
10. Closed-loop automated test passes.

## Persistent GA-004~007 evidence

- Signed website conversion events are normalized by the connector and committed through one PostgreSQL transaction.
- Replayed event IDs return the existing lead without duplicating engagement, score or audit mutations.
- Deterministic email/domain identity evidence reuses the scoped canonical lead; conflicting identities roll back and require human review.
- Score snapshots are immutable and event-idempotent, while distinct events at the same timestamp remain distinct history.
- Customer 360 reads tenant-scoped identities, engagements, score history, opportunities, revenue and audit timeline; cross-tenant reads return no record.

## Governed GA-010 delivery evidence

- The first official-API publishing adapter is disabled by default, HTTPS-only outside tests, host-allowlisted and credential-reference based.
- Every external write carries an idempotency key and an existing validated approval reference; credential values, content bodies and raw error messages are not persisted.
- Delivery registration validates idempotency, adapter, asset and approval references before computing or persisting the request fingerprint. Migration 023 repeats reference-shape and secret-material checks in PostgreSQL, so direct writes containing raw token/JWT-like material fail with a constraint violation before an operation or audit event exists.
- Adapter completion results are also untrusted: external ID/status must be bounded reference-only values before the ledger can become `COMPLETED`. Secret-like responses become sanitized terminal failures, and migration 024 blocks direct database injection into either external reference column.
- Retry classification requires the literal boolean `true`, remaining attempt budget and a valid schedule between 1 second and 24 hours in the future. Missing/invalid schedules and string booleans become sanitized terminal failures instead of immediately executable retry loops. Registration accepts only 1–20 attempts, the two supported operation types and bounded uppercase capability identifiers; migration 026 mirrors operation/capability constraints against direct SQL.
- Official outbound adapters share a strict transport boundary: `enabled`/approval settings are real booleans, timeout is 100 ms–30 s, test-only HTTP is loopback-only, endpoint credentials/query/fragment are forbidden and successful JSON responses are stream-bounded (64 KiB default, 1 MiB hard maximum). Credential tokens are length/control bounded; authoritative ID/status values are safe references, publishing never returns an arbitrary remote URL, and business payloads are finite, depth/node/size bounded and reject credential-like keys or secret-like values.
- Credential resolution itself is independently bounded by the configured timeout before HTTP begins. A hung resolver returns a structured retryable timeout, while resolver exceptions become a sanitized retryable resolution error without propagating vault/provider messages. Invalid returned token shape remains non-retryable and no fetch occurs.
- Delivery retry and reconciliation mutations also default deny inside the PostgreSQL store, not only at the HTTP route. Console injects and passes its evaluated Access Center decision; retry requires the `business.work.control` action capability and reconciliation requires `proposal.approve`. Direct/internal store calls without the narrow authorization seam cannot mutate either state.
- Identity-review decisions follow the same defense in depth: `decide()` defaults deny and Console's injected integration requires its evaluated `proposal.approve` capability. Resolution reasons are 1–500 characters, control-character-free and secret-material-free before authorization; migration 027 mirrors those constraints so direct SQL cannot turn a human-review note into secret storage.
- The PostgreSQL delivery ledger records request fingerprints, CAS versions, bounded attempts, retry classification, external IDs and reconciliation state without creating a second Scheduler or Queue.
- Rate limits and server failures may become `RETRYABLE`; policy/approval failures become terminal. Completed writes can be reconciled as `MATCHED` or `MISMATCH`.

## Governed GA-013 handoff evidence

- Commercial handoff requires an existing approval reference when the downstream adapter declares approval.
- The default-disabled official Business API adapter returns only authoritative downstream references and never promotes Growth projections into CRM/ERP truth.
- RFQ/quote/order handoffs reuse the same delivery ledger and pass only a controlled source reference; commercial payloads and credentials are not copied into the ledger.

## Read-only operations evidence

- `/growth-sales` exposes delivery totals, running/retryable counts and sanitized exception/reconciliation items through a tenant-scoped PostgreSQL endpoint.
- The endpoint returns an explicit unavailable/migration-required status instead of mutating schema during a read.
- The browser projection cannot receive credential references, approval references, request fingerprints, source references or raw error messages, and it cannot trigger retries.

## Governed operator control evidence

- Every delivery transition is captured by a PostgreSQL trigger in an immutable, tenant-scoped audit trail with actor, CAS version, status and sanitized outcome metadata.
- A sales operator with `business.work.control` may only bring an already-`RETRYABLE`, below-limit operation forward to its next eligible execution time; the request does not call an external system or create another worker.
- Reconciliation requires separate `business.manage + proposal.approve` authority, an exact operation version and an observed external ID.
- Sales reviewers cannot request retries or assert reconciliation, and ordinary sales operators cannot assert reconciliation.

## GA-000~017 definition of done
GA-000 architecture/boundaries; GA-001 tenant/domain model; GA-002 channel contract; GA-003 events/audit; GA-004 discovery; GA-005 identity graph; GA-006 scoring; GA-007 360 projection; GA-008 content strategy contract; GA-009 media-factory adapter; GA-010 publishing contract; GA-011 engagement ingestion; GA-012 qualification/NBA; GA-013 downstream opportunity handoff; GA-014 follow-up action; GA-015 revenue attribution; GA-016 optimization inputs/decision action; GA-017 executive closed-loop report.

The current reusable core implements the minimum executable vertical slice for all stages. Production connectors, tenant packs and UI are incremental adapters/surfaces and must not alter the core boundary.

## Pilot policy
KingTurf is the first reference tenant. Its product catalog, ICPs, countries, keywords, scoring weights, content policy, sales playbook and Business OS mappings belong in a tenant/industry pack, never reusable core.

## Pilot readiness evidence

- `pnpm --filter @anksen-agent-studio/growth-core pilot:readiness` evaluates implementation evidence separately from production activation evidence and is part of the root and CI acceptance gates.
- The KingTurf snapshot proves the tenant pack, scoped channel mix, signed website connector, official publishing/business adapter boundaries, persistence migrations, delivery audit/ledger and unrelated second-tenant validation.
- Website webhook HMAC covers the canonical bytes `timestamp + "." + eventId + "." + rawBody`, not the body alone. `x-growth-timestamp` is a 10-digit Unix second within the configured window (default 300 seconds), event IDs are bounded, and replay lookup happens only after signature validation. Changing the event ID or timestamp invalidates the signature; consent flags require literal JSON booleans.
- The verified payload then passes a bounded schema: controlled engagement kinds, reference-only external/product/raw IDs, at most 50 product references, typed contact/consent objects and bounded contact/message fields. `PersistentGrowthIngestionService` repeats the critical reference, kind/high-intent consistency, consent, product-list, clock and future-observation checks before opening a transaction, so direct adapter bypass fails without a database connection.
- The process-local replay cache is capacity-bounded (default 10,000, hard maximum 100,000) with oldest-entry eviction, and webhook bodies are capped at 1 MiB even when configured. Cache eviction does not weaken the closed loop: tenant-scoped PostgreSQL event idempotency remains the durable final replay barrier.
- Canonical relations cannot borrow a globally existing lead/opportunity from another tenant. Store writes use scope-qualified `INSERT ... SELECT`, while migration 028 adds composite tenant foreign keys for identity, engagement, score, opportunity and both revenue relationships. PostgreSQL acceptance verifies all six constraints and application rejection paths.
- Canonical identities accept only `EMAIL`, `PHONE` and `DOMAIN`. The Store applies type-specific lowercase/canonical validation (including phone punctuation removal and host-only domains), bounds source vocabulary, and migration 029 repeats enum, length, lowercase, control-character, type-shape and source constraints for direct SQL.
- Every Growth tenant scope identifier now uses the shared 1–128 character index-safe grammar `[A-Za-z0-9][A-Za-z0-9._:/-]*`. Growth Core rejects invalid organization/workspace/tenant IDs before any adapter or Store work, and migration 030 installs the same constraint on all 15 authoritative scope-bearing Growth tables; acceptance verifies the constraint count and a direct-SQL rejection.
- Canonical event conflicts are no longer blindly treated as duplicates. After `ON CONFLICT`, the store accepts only an exact same-tenant idempotency match across type, subject, source, JSON payload, schema version and occurrence time, returning the canonical existing event ID. Cross-tenant event-ID collisions or same-key payload drift fail with `GROWTH_EVENT_IDEMPOTENCY_MISMATCH_OR_SCOPE_CONFLICT`.
- New canonical events additionally require the eight Growth event types, safe bounded references, schema version 1–100, an object payload no larger than 64 KiB and a valid occurrence time no more than five minutes ahead of the injected clock. Migration 031 enforces the structural contract as `NOT VALID`: all new/direct writes are checked immediately, while pre-contract immutable fixture/history rows do not block rollout and require a separately governed retention migration before eventual validation.
- Canonical lead roots now validate before SQL: safe 160-character ID, bounded source, uppercase state, object-only person/company (32 KiB each), array-only external refs (64 KiB), nullable object score (64 KiB), safe market/ICP refs and created time no more than five minutes ahead. Migration 032 mirrors structural limits as a rollout-safe `NOT VALID` check that immediately covers all new rows.
- Canonical engagements now reject unsafe engagement/lead references, uncontrolled kind or channel values, non-object or over-64 KiB payloads, invalid clocks and occurrence times more than five minutes ahead before SQL. Migration 033 mirrors the structural contract for every new/direct row with rollout-safe `NOT VALID` semantics.
- Canonical score snapshots validate safe IDs/model/policy references, uppercase score type, finite value 0–100 and confidence 0–1, array/object 64 KiB evidence envelopes and non-future calculation time before SQL. Reusing a snapshot ID is accepted only for an exact immutable replay. Migration 034 enforces the structural portion for every new/direct row.
- Canonical opportunity and revenue writes validate safe relation IDs, uppercase stage, optional score 0–100, object-only 64 KiB downstream/metadata envelopes, non-negative finite attribution amount, ISO-style uppercase currency and non-future attribution time before SQL. Opportunity IDs cannot be rebound to another lead, and revenue IDs accept exact immutable replay only. Migration 035 mirrors structural limits for direct writes.
- Connector binding configuration and health evidence validate bounded adapter/binding/actor IDs, positive CAS versions and a finite clock before authorization or SQL. Migration 036 constrains new direct binding rows, including reference-only credentials, DNS endpoint hosts, versions and SHA-256 health hashes; it does not enable a connector or Runtime.
- Customer 360 validates the lead reference before SQL and independently limits identities, engagements, score history, opportunities, revenue and timeline to the latest 200 records. Connector audit reads retain chronological presentation while fetching at most the newest 500 rows, preventing tenant history growth from creating unbounded read amplification.
- Identity resolution now validates the canonical lead reference before its atomic insert/select path; secret-like, malformed or overlong references never reach SQL. Migration 037 mirrors lead reference structure for every new direct row (identity IDs remain native UUIDs) while preserving the normalized type/value/source checks from migration 029.
- Delivery register, attempt, completion, failure, retry and reconciliation paths now validate operation/actor/external references, positive CAS versions and finite clocks before authorization or SQL. Reconciliation observations are reference-only, delivery audit reads cap the newest 500 rows, and migration 038 constrains operation IDs, SHA-256 fingerprints, actors, counters and bounded error envelopes for new direct rows.
- Identity review listing/decision validates clocks, case/actor/selected-lead references, positive versions and dismissal semantics before authorization or SQL; audit reads cap the newest 500 rows. Migration 039 constrains case/idempotency/source/hash roots, 2–20 candidate leads, the EMAIL/PHONE/DOMAIN evidence vocabulary and resolution actors for new direct rows.
- Tenant production feature-flag mutations validate actor references and positive optional CAS versions before the production authorization callback or database connection. Migration 040 requires disabled rows/events to clear authorization reference/hash and expiry, and constrains flag/event IDs, actors, versions and SHA-256 evidence structure for new direct writes.
- Connector activation preflight/activate/emergency-disable validates request/binding/incident/actor references, positive versions, finite clocks and secret-free bounded reasons before access authorization or SQL. List preflight timestamps are also fail-closed. This hardening does not add an activation UI, bypass Production Ops policy or perform an activation.
- Runtime readiness evidence rejects malformed, overlong or secret-like exact binding fields before SQL. Credential-reference and runtime-health probe exceptions become explicit readiness blockers and never cascade into Runtime startup; health is probed only after every authoritative database/feature/credential prerequisite passes.
- Tenant source-approval readiness validates organization/workspace/tenant/application identifiers and a finite clock before SQL, and caps the connector evidence projection at 100 rows. The shared business source request/decision workflow remains unchanged; Growth consumes only the bounded, credential-value-free readiness projection.
- Publishing readiness accepts at most 20 unique, bounded, secret-free platform labels, validates its clock before SQL, reads at most 100 active channel accounts, ignores unsafe credential-reference rows and accepts authorization evidence no more than 366 days ahead. It exposes only readiness counts, never credential references or values.
- Each persistent website ingestion captures and validates exactly one clock snapshot. The transaction Store, scoring result, lead creation, engagement/event occurrence fallback and post-rollback identity-review record all reuse that same instant, preventing clock-provider drift inside one canonical event transaction.
- A single canonical revenue attribution is bounded to 1,000,000,000,000 currency units before SQL; migration 041 applies the same ceiling to new direct rows. Together with the 200-row Customer 360 history cap, this keeps its JavaScript aggregate within a reliable finite operational range without performing currency conversion.
- The snapshot truthfully remains `PILOT_ACTIVATION_BLOCKED` while credential references, connector health, data-owner approval, production feature flag, Runtime Activation Gate or explicit production authorization are absent.
- Readiness assessment is pure and read-only: it cannot resolve credential values, invoke connectors, mutate production, or enable a Runtime.
- The authenticated Growth Console projects the same versioned report and its blockers through a read-only endpoint; it exposes no activation control and rejects an explicitly different tenant context.
- Console delivery-failure and reconciliation-mismatch counts come from the tenant-scoped PostgreSQL ledger. Missing tables/connections and the not-yet-persisted identity-review backlog remain unobserved blockers; absence of evidence is never converted to zero.
- Conflicting deterministic identities roll back the lead mutation, then idempotently create one tenant-scoped identity-review case containing only candidate lead IDs, identity types and a hashed external reference. The readiness backlog is counted from open persisted cases.
- Identity-review resolution or dismissal requires the dedicated sales-review action, an exact case version, a reason and—for resolution—a lead from the recorded candidate set. PostgreSQL triggers preserve opened/resolved/dismissed audit events; the browser remains read-only and omits raw identity values and external references.
- Publishing Credential Reference presence is derived from active, unexpired, tenant-workspace-scoped `channel_account` business records. The projection returns only a configured count and `credentialValuesRead: false`; account configuration is reported as `CONFIGURED_NOT_PROBED`, never promoted to connector health.
- Authorization expiry uses a strict `expiresAt > now` rule for channel accounts and connector activation. At the exact expiry instant the Credential Reference is absent from readiness and the activation request is blocked, matching source-approval and feature-flag semantics.
- Website ingress, publishing and Business API bindings have one tenant-scoped governed registry. Bindings store reference IDs and allowlisted hosts—not credential values—are default-disabled, use CAS for configuration and hash health evidence. Readiness reports missing bindings, disabled state and stale probes as blockers; no probe or activation is performed by assessment.
- Connector configuration and health-evidence persistence have one injected mutation-authorization seam whose default is deny. Health probes additionally require authorization before binding context is read or an adapter can be called. A read-only Console store can project readiness but cannot register/reconfigure a binding, contact a probe target or certify health; local integration fixtures must explicitly authorize each seam.
- The health-probe seam accepts only adapters declaring `READ_ONLY_HEALTH_PROBE`, permits pre-activation probing of disabled bindings but rejects stale versions, passes a Credential Reference identifier rather than resolving a value, and returns explicit `externalWritesPerformed: false`. Raw probe evidence is hashed before persistence and omitted from audit/readiness projections.
- Health timestamps later than the assessment clock are treated as `STALE` even when within the write-side clock-skew tolerance. The activation Gate independently repeats the future-time rejection, so predated/future evidence cannot satisfy production health readiness.
- Connector activation reuses the conventional Growth `connector_activation` record and existing `business_approval`; it does not add an approval engine. The approval must be the exact transition that produced the current approved record version (`object_version + 1`), not merely any historical approval on the object. The Gate separately requires `production.request`, exact request/binding versions, matching tenant/kind, fresh healthy evidence, an unexpired explicit authorization reference and one-time atomic consumption. No Console activation endpoint or button is exposed.
- The authenticated Console exposes a tenant-scoped, read-only activation-preflight list for production-operations handoff. It returns current request/binding versions, health status and blocker codes only; Credential References, explicit authorization identifiers, approval comments and raw probe evidence remain server-side, and the projection performs no external call or activation.
- An authorized emergency-disable operation provides the post-activation rollback path: it requires `business.manage + production.request`, the exact enabled binding version, an incident reference and a bounded reason. It atomically disables only the scoped binding, hashes the reason, appends an immutable incident event, makes no external call and fails closed on replay. No Console disable endpoint is exposed.
- The named `growth_production_operator` role is the separated execution persona. It may pass Access Center checks for governed activation and CRITICAL emergency disable, but has no `business.operate`, `proposal.approve`, access-management or Runtime-execution capability.
- Access Center authorization is necessary but not sufficient: the Gate has a second injected Production Ops authorization seam whose default is deny. The role-only integration path is rejected with `GROWTH_CONNECTOR_PRODUCTION_OPERATION_NOT_AUTHORIZED`; only an explicit local governance fixture proves the remaining transaction path. This preserves the repository-wide `production_operations: disabled` policy.
- The read-only `GrowthProductionOperationsPolicy` bridge reuses the existing `@anksen-agent-studio/production-ops` bundle and release-gate evaluator. Console preflight reports the authoritative `production-operations-blocked` gate, `dry_run_only` mode and forbidden production-operation policy; missing gates also fail closed. The bridge cannot mutate policy, call an external system or turn authorization on.
- `PRODUCTION_OPERATIONS_POLICY` is also a first-class Pilot activation check. The authenticated readiness route replaces versioned fixture input with the current central gate result, so a stale snapshot cannot claim activation readiness while the repository-wide policy is blocked.
- `DATA_OWNER_APPROVAL` is no longer trusted from the Pilot JSON in the authenticated route. Migration 018 extends the existing Business Source Governance approval with tenant scope and expiry; Growth accepts only active non-fixture application sources whose latest same-tenant approval is approved, mapped, credential-reference configured and unexpired. Other tenants, expired approvals, missing migrations and zero registered sources all fail closed without returning credential values or decision reasons.
- Migration 020 gives Business Source approvals a monotonic sequence. Both connector readiness and tenant Pilot readiness select the latest sequence, so equal timestamps cannot make an older approval/revocation win nondeterministically. A revoke followed by same-clock replacement approval is covered by PostgreSQL evidence.
- A fresh Business Application Runtime now always applies the idempotent Growth governance migrations after bootstrapping the base Kernel/business schema under the shared migration lock. First startup therefore receives migrations 018–020 without relying on a separate Growth database initializer.
- Business Runtime and Growth initialization share `growth_schema_migration` under advisory lock `16012027`. Each applicable 012–025 script runs once per database, preventing repeat trigger/ALTER DDL from deadlocking with business transactions in concurrent Console/test processes. Migration 021 also creates its trigger conditionally rather than dropping and recreating it.
- The shared migration runner records the SHA-256 of every applied Growth script. Pre-checksum ledger rows are backfilled once from the checked-in script; after that, a same-name content mismatch fails with `GROWTH_SCHEMA_MIGRATION_CHECKSUM_MISMATCH` before any script runs. Root acceptance proves insert, idempotent replay and drift rejection against PostgreSQL.
- Migration 022 applies the same PostgreSQL UPDATE/DELETE rejection to canonical Growth events, score snapshots, delivery events, identity-review events and connector-binding events. Acceptance verifies all five triggers exist and exercises SQLSTATE `55000` against a canonical event; retention/deletion is outside ordinary application permissions.
- `PRODUCTION_FEATURE_FLAG` is backed by migration 019 and a tenant-scoped CAS store, not user/plan beta features. A missing or expired flag is disabled; enabling requires a bounded authorization reference and expiry, while both enable and exact-version disable require a separate injected Production Ops authorization whose default is deny. The mutation boundary requires a real boolean, so strings such as `"false"` cannot become truthy enables, and flag keys use a bounded uppercase identifier grammar. Events retain only a hash of the authorization reference, migration 021 rejects database UPDATE/DELETE attempts with SQLSTATE `55000`, and migration 025 independently constrains keys and secret-like authorization material against direct SQL bypass. Readiness exposes no reference and the Console has no flag mutation endpoint.
- `RUNTIME_ACTIVATION_GATE` is read through an adapter over the existing Orchestrator policy/worker/approval/credential-reference tables. It requires an exact project/goal/task/worker/policy/approval binding; absent KingTurf binding is `NOT_BOUND`. Credential and Runtime health probes default deny, the CODEX feature flag must be explicit, and assessment never consumes approval or starts Runtime.
- When a tenant pack declares `metadata.runtimeActivationBinding`, Core validates and freezes the seven-field existing Activation Gate contract and rejects missing fields or non-CODEX Runtime types at load time. The field remains optional, so the KingTurf pack intentionally stays unbound and blocked until governed IDs exist; no synthetic Runtime objects are created.
- The PostgreSQL Runtime evidence adapter repeats the CODEX-only check at its trust boundary. Direct callers presenting `CONTROLLED_STUB` or another Runtime type receive `RUNTIME_TYPE_UNSUPPORTED` before any database query or readiness probe, so tenant-pack validation is not the sole defense.
- Credential-reference and Runtime-health checks are short-circuited until the exact approval, policy, worker, credential binding and CODEX feature flag all exist. A globally disabled Runtime therefore causes zero injected probe calls rather than collecting unnecessary production evidence.
- `EXPLICIT_PRODUCTION_AUTHORIZATION` is derived from the governed connector-activation preflights rather than the Pilot JSON. Coverage requires one currently `READY` request for each required connector kind—website ingress, publishing and business handoff. Duplicate requests cannot substitute for a missing kind, and the readiness projection exposes only kind coverage and blocker counts, never authorization references.
- Explicit activation and production feature-flag authorization references reject common secret material shapes in addition to key/value patterns: OpenAI-style `sk-`, GitHub tokens, Bearer material, PEM headers and JWT-like values cannot be persisted or accepted as governance references.
- Connector activation and production feature flags cap authorization lifetime at 366 days by default. A future timestamp is insufficient when it exceeds that bounded window, and invalid health/authorization policy windows fail during construction rather than silently weakening the Gate.
- Injected policy parameters cannot widen those ceilings: connector health freshness is at most 24 hours and production authorization at most 366 days. Non-finite clocks and freshness inputs fail explicitly across activation, feature-flag and connector-readiness boundaries instead of disabling expiry arithmetic through `NaN` comparisons.
- Health evidence writes validate a finite local clock and a trimmed, control-character-free, non-secret reference of at most 512 characters before calling mutation authorization or PostgreSQL. Only its SHA-256 enters storage; invalid probe output cannot create an unbounded hash input or partially authorize a write.
